================================================================
 MODULE FORGE - HOW TO MAKE CUSTOM MODULES WITH JSON
================================================================

Module Forge is a SEPARATE mod from Weapon Forge. It lets you create
custom MODULES - the small grid upgrades you attach to your ship or
weapons (like Health Up, or +Firerate, or Extra Projectile). Custom
modules can drop from crates/bosses and/or be bought in the shop.

No programming needed: the DLL does the work; the JSON files are the
modules. Every *.json in the "modules" folder (next to ModuleForge.dll
in BepInEx\plugins) becomes a module.

----------------------------------------------------------------
 1. HOW IT WORKS
----------------------------------------------------------------

At game startup, Module Forge reads each modules/*.json, clones a
stock module of the right kind as a shell, swaps in your effects, and
registers it so it works with save/continue. It then makes the module
available in loot and/or the shop per your settings.

Edits are read at STARTUP - restart the game to see changes.

"target" says which KIND of module this is:
  ship    -> an UPGRADES card (stat ups, regen, shields, drains)
  weapon  -> a WEAPON MODS card (fire rate, projectiles, explosions)

WHAT THAT ACTUALLY CHANGES, because it is less than it sounds and
this file used to say otherwise ("a module attaches to ONE of two
places"). It picks which stock module is cloned as the shell, and the
shell's type decides three presentation things: the word printed at
the top of the module card (UPGRADES or WEAPON MODS), which section
of the shop it is listed under, and the background art behind its
icon. Nothing else - the two shells are otherwise identical assets.

IT DOES NOT DECIDE WHERE YOU CAN PUT IT. Every ordinary cell in the
grid is a "Normal" slot, and a Normal slot accepts both types (plus
power cores and boosters); only the six special slots - the ship
core, the two weapon mounts and the three ability slots - are picky.
So a "ship" module can be connected into a weapon's cluster and a
"weapon" module can be connected around the ship core, and the game
will run it there.

AND FOR SCOPE, WHERE YOU PUT IT IS THE ONLY THING THAT COUNTS. An
effect that behaves differently per grid - KillRewardEffect,
CritEffect, LeechEffect - reads the grid it is actually connected
to, never this field. Set "target" to whichever shelf you want the
module to appear on; slot it wherever you want it to act.

A MODULE MUST BE CONNECTED AND POWERED TO DO ANYTHING
-----------------------------------------------------
This is the game's rule for its own modules and Module Forge now
keeps it too. A card lying loose in the grid, or connected but
sitting outside its cluster's power core, has NO effect - and it
starts working the instant you plug it in, with no restart.

You can already see which is which without reading anything: the
grid draws an unconnected or unpowered icon differently, and the
game's own hover card counts such a module as not installed.

CHANGED 2026-09-11, AND IT USED TO BE WRONG HERE. Every effect that
registered something when the card was placed - on-kill payouts,
crit, leech, ship stats, pierce, phasing, burn rate and colour,
stealth, last stand, invulnerability, ammo - registered on PLACEMENT
and never checked again. So an unpowered module kept working. The
on-kill ones failed the worse way round: never having been handed a
weapon, an unpowered card sitting in a WEAPON's cluster paid out for
every gun on the ship rather than for that one.

Nothing in any module file changes. If a module of yours suddenly
appears to do nothing, check the power before you check the JSON -
and look in the log for a line naming the card, which is said once
per run each way (switched off, and switched back on).

The three effects that only touch a weapon - CellConvertEffect,
ExtraWeaponStatEffect, WeaponResourceEffect - never had the problem:
the game only offers a weapon the modules in its cluster that are
already connected and powered.

----------------------------------------------------------------
 2. QUICK START
----------------------------------------------------------------

  1. Install ModuleForge.dll in BepInEx\plugins (its own folder).
  2. Run the game once - a "modules" folder appears next to the DLL
     with example files + a README.
  3. Easiest: open "Module Builder.html", design a module, click
     SAVE .JSON FILE, and drop it in the modules folder.
  4. Restart the game. The module now drops / is in the shop.

Problems are logged to Module Forge's own log - a bad file is
skipped, never crashes the game:
     <game>\BepInEx\ModuleForge.log

THE LOG FILE (since 2026-09-25). Module Forge writes everything to
ModuleForge.log, beside BepInEx's own LogOutput.log, so LogOutput.log
stays readable for BepInEx and any other mods you run:
  - ModuleForge.log is THIS launch. It starts with the BUILD stamp.
  - ModuleForge.prev.log is the launch BEFORE, kept so a restart or
    a quit to the desktop does not wipe the session you wanted.
  - LogOutput.log keeps Module Forge's "loaded" and BUILD lines, and
    a copy of every ERROR, so a broken file is still visible there.
    Warnings and ordinary lines are only in ModuleForge.log.
  - The BepInEx console window shows the same as LogOutput.log.
  - If the GAME itself throws an error whose stack trace names
    Module Forge, a copy goes in ModuleForge.log too. BepInEx leaves
    the game's own errors out of LogOutput.log by default, so this
    file is the only place those are written down.
  - Two copies of the game at once: the second writes
    ModuleForge.2.log and says why at the top.
  - Want it all back in LogOutput.log? Set [Logging] OwnLogFile =
    false in BepInEx\config\com.sugarheady.moduleforge.cfg.

----------------------------------------------------------------
 3. FILE STRUCTURE
----------------------------------------------------------------

{
  "name": "GlassCannon",        <- REQUIRED, unique id. Spaces are
                                   fine ("Glass Cannon" works); just
                                   do not reuse a name the game has,
                                   and do not leave a space at the
                                   start or end.
  "displayName": "GLASS CANNON",
  "description": "...",
  "target": "weapon",           <- "ship" or "weapon" (default ship)
  "icon": "HUD_GridTiles_10",   <- module icon sprite (section 6)
  "color": "#ff5555",           <- icon tint: game color or #hex
  "source": "both",             <- "loot" / "shop" / "both" / "none"
  "shopPrice": 150,             <- shop cost in money
  "shopPriceIncrement": 500,    <- added per purchase (0 = fixed price)
  "shopUnlockLevel": 2,         <- stations to unlock first (0 = first)
  "lootWeight": 10,             <- drop chance vs other modules
  "effects": [ ...one or more effect objects... ]   <- REQUIRED
}

A module can carry SEVERAL effects, and you can MIX buffs and debuffs
(e.g. +1 projectile AND -20% fire rate). Just list them all in
"effects".

----------------------------------------------------------------
 4. VALUES
----------------------------------------------------------------

Any magnitude can be a plain number (flat, e.g. "value": 1) or a
scaling object that grows with module level:
    { "baseValue": 2, "increaseMethod": "Add", "change": 1 }
Flat numbers are simplest and level-independent. NEGATIVE numbers are
allowed and do the opposite (e.g. -0.2 fire rate = -20%).

----------------------------------------------------------------
 5. EFFECTS
----------------------------------------------------------------

SHIP effects (use with "target": "ship"):
  ModifyResourceCapacity  { resource, amount }        +/- a tank's max
  ResourceAutoChargeEffect{ resource, amount }        regen per second
  DrainResourceEffect     { resource, amount }        drain/sec (neg=gain)
  AddShieldEffect         { resource, amount }        shield; 0.5 = 50%

EITHER GRID - works with "target": "ship" OR "weapon". Which grid you
put one in decides its SCOPE, and that is free rather than a flag:
  CritEffect       a chance for hits to do multiplied damage
  LeechEffect      your hits heal you
  KillRewardEffect pays out when you kill something

  "Which grid you put one in" means exactly that - where you slot the
  card in game, not what "target" says. A "ship" module connected into
  a weapon's cluster scopes to that weapon, and a "weapon" module
  connected around the ship core covers every gun. See section 1.

  KillRewardEffect (alias "onKill")
     { resource, amount, asPickup, chance, maxPerSecond, clearBurn,
       coolHeat, buffDuration, buffFireRate, buffDamage, buffMaxStacks,
       buffIndicator, gas }

  Pays out when the ship KILLS something.

  WHOSE KILLS COUNT IS DECIDED BY WHICH GRID YOU PUT IT IN, and you do
  not set a flag for it:
     on the SHIP grid    -> any weapon's kills pay out
     in a WEAPON's grid  -> only THAT weapon's kills pay out

  That falls out of the game's own architecture rather than being
  invented: WeaponFactory only walks the modules in a WEAPON's cluster
  when it applies IWeaponModifier, so a ship-grid module never gets that
  call and a weapon-grid one does. The module's card says which it ended
  up as ("Counts kills by: this weapon" / "any weapon").

  THE GAME CREDITS KILLS FROM ONLY THREE PLACES - a projectile hit, a
  beam hit and an explosion - and records only which UNIT killed, never
  which weapon, so the weapon is tracked by this mod. Nothing else
  credits a kill at all, not even Die() itself.

    resource / amount   which tank, and how much per kill. amount takes
               a per-level series, so BoosterCores raise the payout.
               Clamped to the tank's capacity - it cannot overfill.
    asPickup   drop a real pickup on the corpse to fly through instead
               of granting it instantly. Missable, and more visible.

               FIXED 2026-08-23 - it used to stop working silently, and
               often before it worked at all. The pickup to copy was
               learned only from pickups that had already SPAWNED in the
               room, and the fallback search could not see prefabs, so:
               a kill before any crate had dropped anything found
               nothing, latched a "searched" flag, and disabled the
               feature for the whole run. Worse, a pickup DESTROYS
               itself when collected, so a cached one silently became
               null the moment you picked it up. It now reads the eight
               pickup PREFABS directly, which are never destroyed.

               THE GAME SHIPS NINE, and nearly every resource has one:

                 Fuel      blue orb        (prefab "FuelPickup")
                 Caps      orange orb
                 Purple    pink orb
                 White     white
                 Health    red             (prefab "ResourcePickup_Red")
                 Tech      purple squares
                 Money     yellow, three sizes for 10 / 20 / 50

               Two are named nothing like their resource: HEALTH IS
               "ResourcePickup_Red" and FUEL IS "FuelPickup". You never
               type either - you name the RESOURCE and the right prefab
               is found for you. The only stock resource with no pickup
               of its own is ELECTRON.

               A resource with no pickup prefab of its own borrows the
               orb and RE-TINTS it to that resource's own colour, so
               only the shape is borrowed - and if even that is
               impossible the resource is granted straight into the tank
               instead. Either way THE REWARD STILL PAYS. It used to
               warn that it was "granting it directly" and then grant
               nothing at all.

               FIXED AGAIN 2026-08-26 - the 2026-08-23 fix above was
               written but never ran. The prefab scan guarded itself on
               "have I got anything cached yet", and a separate path
               fills that same cache from every pickup the game spawns -
               so the first crate to drop anything skipped the scan for
               the rest of the run, and the art fell back to whatever
               was lying around the room. Same wrong art all run, a
               different wrong art next run.

               A substitution now LOGS a warning naming the resource
               and the prefab it borrowed, so wrong art is never a
               mystery again.
    chance     0-1, and also a series - so a level can buy RELIABILITY
               rather than size. Rolled before the cap, so a failed roll
               does not consume it.
    maxPerSecond
               cap on how much RESOURCE this grants per second, 0 =
               uncapped. The case this exists for: one explosion can
               kill a dozen enemies in the same frame.
               CHANGED 2026-08-18. It used to count PAYOUTS per second,
               which is not how it reads next to "amount" - "amount": 3
               with "maxPerSecond": 4 obviously means 4 fuel a second,
               not 4 kills a second. RETUNE EXISTING FILES. A module
               that grants no resource (buff-only, burn-only) still
               counts payouts, so it keeps a limiter either way.
    clearBurn  burn level removed from your own ship per kill - as in
               your ship is ON FIRE. NOT the "overheat" meter; that is
               "coolHeat" below, and the two read as the same word on
               the module card until R15 (both said "cools"). The only
               payout that can save you mid-fire. The ship sheds burn at
               5/second by itself.

    coolHeat   heat removed from a weapon's OVERHEAT meter per kill, in
               the same units as that block's "max" and "perShot".

               NEEDS WEAPON FORGE. "overheat" is a per-weapon block from
               a Weapon Forge weapon FILE, so with that mod absent there
               is no meter in existence to take heat off. Module Forge
               deliberately does not grow a heat system of its own to
               fall back on - one owner per mechanic is the rule these
               two mods are built on, and a second implementation would
               be two engines fighting over one meter. Without Weapon
               Forge this key warns at build time, the card says so, and
               the rest of the module works normally.

                   { "type": "onKill", "coolHeat": 25 }

               THE PART WORTH DESIGNING AROUND: a kill that drops the
               meter below the weapon's "ventTo" also ENDS A VENT
               LOCKOUT on the next frame, through the same path a normal
               cooldown uses - so the recover sound, the repaint and the
               fire-rate restore all happen properly. Slot this next to
               a gun that jams hard and it stops jamming while you are
               connecting.

               SCOPE is the usual rule for this effect and needs no
               flag: in a WEAPON's grid only that weapon's meter cools;
               on the SHIP grid whichever gun scored the kill does.

               "In a weapon's grid" is about where you SLOT the card,
               not about "target". A module built with "target":
               "ship" cools only one gun once you connect it into
               that gun's cluster. Set "target": "weapon" when you
               also want it filed under WEAPON MODS in the shop.

               Weapon Forge can do the same thing from the weapon file
               itself - "coolHeat" inside its "onKill" block. Use that
               when the gun should always have it; use this when it
               should be something you find and slot.
    buffIndicator
               SHOWS THE BUFF ON SCREEN while it lasts, wearing this
               module's own icon and colour. "feed" (the game's own
               status line - the one that says FUEL LOW), "icons" (a row
               beside the minion counter), "both", or "off". Leave it
               out to follow the global default.

               The feed is not a hack: the game already uses that line
               for PERSISTENT status, not just messages. "Fuel low" is
               logged with no duration, coloured and flashing, then
               cleared when it stops applying - the same shape as a
               buff.

               The global default and the label live in
               BepInEx/config/com.sugarheady.moduleforge.cfg:
                 Style   off / feed / icons / both
                 Label   effect (FIRE RATE +30%) / seconds / stacks /
                         icon
               Weapon Forge keeps its OWN copy of these settings so
               either mod works alone. If both are installed and the two
               disagree, the log says so once at startup - module buffs
               and weapon buffs will simply look different on screen.
               With both installed you get ONE icon row, not two, and a
               weapon buffed from both sources shows TWO lines, one per
               source, each wearing its own icon - so you can see which
               module is pulling its weight.

               This one shows on the module card like every other
               setting.
    buffDuration / buffFireRate / buffDamage / buffMaxStacks
               a timed weapon buff. The bonuses are FRACTIONS (0.25 =
               +25%) and need a duration or they do nothing. On the SHIP
               grid the buff applies to every weapon you are holding; in
               a weapon's grid, only to that weapon. maxStacks 1 means
               each kill refreshes rather than stacks.

    gas        A LINGERING CLOUD LEFT ON EVERY CORPSE. A block, not a
               number - this is the one reward here that describes a
               thing rather than a quantity.

                 { "type": "onKill",
                   "gas": {
                     "damagePerSecond": 2.5,
                     "burnPerSecond": 1.5,
                     "duration": 3.5,
                     "radius": 1.1,
                     "growTo": 2.4,
                     "slow": 0.4,
                     "color": "#8CF266",
                     "max": 22
                   } }

               IT WORKS WITHOUT WEAPON FORGE, and that is the difference
               between this key and "coolHeat" above. An overheat meter
               only exists inside a Weapon Forge weapon FILE, so there is
               nothing for a local copy to act on and "coolHeat" bridges
               instead. A cloud has no such dependency - it is an object
               in the world - so Module Forge grows its own and a gas
               module works with any stock gun.

               AND IT IS NOT SPELLED THE WAY WEAPON FORGE SPELLS IT, on
               purpose. Over there you write:

                 "gas": { ...the cloud... },        <- on the WEAPON
                 "onKill": { "gas": true }          <- a switch

               because the weapon has already described its cloud higher
               up the same file and the switch only decides WHEN one
               appears. A module has no weapon file to point at, so here
               the block itself IS the description. If you copy a weapon
               file's "onKill": { "gas": true } into a module, nothing
               happens and the build log says the block carries no
               payload.

               THE PAYLOADS - set at least one or no cloud is made:
                 damagePerSecond   the cloud's own damage. The only
                                   payload that scales, and the only one
                                   that touches the fireproof Tablet.
                 burnPerSecond     sets things alight using the game's
                                   own fire. Cheap and stacks with
                                   everything, but the game's burn damage
                                   is FLAT - this buys duration, not
                                   intensity.
                 slow              0-1, fraction of speed bled per second.
                 push              outward shove per second. NEGATIVE
                                   PULLS IN, which is the better half.
                 extinguish        takes burn OFF units inside, your own
                                   ship included. A support cloud.
                 igniteTerrain     sets the GROUND alight from the air.
                                   The game only ever ignites terrain on
                                   a projectile collision, so a cloud has
                                   no other route to it.
                 extinguishTerrain puts terrain fires out. CALIBRATE IT:
                                   cell fire thresholds are not
                                   normalised. CellType_Solid - ordinary
                                   rock - ignites at 45 and is re-lit by
                                   every burning neighbour each frame,
                                   while Slime is 1, Tuff 1.3, Moss 2.5.
                                   So 6 douses moss and can NEVER beat
                                   rock. Use about 120 for stone.

               THE SHAPE:
                 duration          seconds each cloud lives. After the
                                   payload this is the number that
                                   decides what the module is.
                 radius / grow / growTo / growTime
                                   it swells from radius to growTo by
                                   default, which reads most like gas.
                                   "grow": false stalls it at one size.
                 fade              seconds of fade-out at the end.
                 max               how many clouds THIS MODULE may have
                                   alive at once; the oldest FADES to
                                   make room. The budget belongs to the
                                   module, so two copies of the same card
                                   share one allowance rather than
                                   doubling it. 0 = unlimited.
                 tickRate          seconds between applications, 0.25 by
                                   default (what the game's own beams
                                   use). NOT a strength knob -
                                   damagePerSecond means per second
                                   whatever this is. A tiny value is
                                   LOUD, not strong: every application
                                   drives a hit flash, a hit sound and
                                   the aggro event.

               "chains" - THE ONE TO UNDERSTAND. Default TRUE. A kill
               scored BY A CLOUD leaves another cloud, so a packed room
               chains through itself. That reads like a runaway and is
               not one: every enemy dies exactly once and one death pays
               out once, so the clouds a fight can produce are bounded by
               how many things are in it. It walks through a crowd and
               stops. Set false for one cloud per kill you scored
               yourself.

               "damageType" - LEAVE IT OUT almost always. Blank means the
               cloud inherits the element of whichever gun scored the
               kill, so it is resisted and coloured like that weapon.
               That is what keeps ONE ship-grid module sensible across
               every weapon you carry, and it is resolved per cloud, so
               two clouds from one module can carry different elements.
               Name one only when the MODULE is the source of the element
               rather than the gun.

               "hitPlayer" - off by default; the clouds cannot hurt you.
               "extinguish" reaches you either way, because putting your
               own fire out is the point of an extinguisher gas.

               "sprite" - GAME sprites only, and blank is right for
               nearly every cloud (the default is a generated soft blob).
               Custom PNGs live in Weapon Forge's sprites folder and are
               deliberately NOT read here: that loader rebuilds what it
               returns at the module-icon size, 24x24 at PPU 40, which is
               wrong for a puff. A multi-frame name only animates if you
               ask - "name:0-8" or "name@12" - so nothing already written
               starts moving on the next launch.

               "sfx" plays ONCE PER CORPSE. With chains on in a crowded
               room, that is a lot of one sound.

               NOT PORTED FROM THE WEAPON SIDE, because they describe a
               PROJECTILE and a module has none: the gas TRAIL (gas laid
               along a flight path), puffGravity / puffDrag /
               puffPierceTerrain (they edit the shot's rigidbody), and
               impactOnly / bloomOnDeath / bloomOnImpact (they choose
               where in a shot's life a cloud appears - a kill is one
               instant). Their absence is deliberate, not an oversight.

               The cloud shows on the module card: what it leaves, its
               damage, burn and slow, and whether cloud kills chain.

  ContactDamageEffect (aliases "contactDamage", "contact", "ram",
                       "spikes")
     { damage, damageType, scaleBySpeed, damagePerSpeed, minSpeed,
       maxDamage, push, recoil, repeatDelay, detect, radius,
       whileBoosting, ignoreSelfDamage,
       tint, tintPulse, tintStrength, tintMode }

  YOUR SHIP DAMAGES WHAT IT TOUCHES.

  THE GAME HAS NO PLAYER CONTACT DAMAGE AT ALL, which is what makes
  this worth a module rather than a tweak. Twelve enemy prefabs carry
  a Hazard and four beak enemies carry a ChargerHead - but the ship's
  own ImpactDamage is SELF damage, and the game only switches it on
  while you are sprinting.

  THIS ONE IS SHIP-ONLY AND WORKS THE SAME IN EITHER GRID, which is a
  deliberate exception to how every other effect here is scoped. The
  others use the free trick - a module in a weapon's grid affects that
  gun, one on the ship grid affects all of them. The thing being armed
  here is your HULL, and there is one hull however many guns are bolted
  to it, so "only this weapon's hull is spiky" has no meaning. The card
  says so out loud.

    damage     FLAT damage per target touched, matching every stock
               Hazard (a Maggot's beak is a flat 3).

    damageType LEAVE IT BLANK for Health. That default is load-bearing
               rather than lazy: a contact hit has NO WEAPON to inherit
               an element from the way a projectile does, and the game
               REFUSES damage with no type without saying anything.
               That exact gap cost two test rounds on the weapon side -
               "they bump into each other and doesnt seem to hurt one
               another".

    scaleBySpeed / damagePerSpeed / minSpeed / maxDamage
               damage from HOW FAST YOU WERE GOING instead of the flat
               number. This is what turns the module from "touching
               things hurts them" into "ramming does" - minSpeed is a
               floor you have to beat to hurt anything at all. The flat
               "damage" value is IGNORED in this mode.

    push       shove what you hit, along your direction of travel.
    recoil     and bounce YOUR ship backwards, exactly as ChargerHead
               recoils off what it bites. Without some of this a shoved
               enemy ploughs away and the impact reads as nothing
               having happened to you.

    repeatDelay
               seconds before the SAME target can be hit again, so
               ploughing through a crowd hits each of them once rather
               than the first one fifty times. Stock ChargerHeads use
               0.3 and 0.5.

    detect     HOW CONTACT IS NOTICED, and the wrong answer fails only
               on your hardest hits - which reads as the feature being
               unreliable rather than as a setting.

               "swept" (the default) casts along where your ship will
               be before the next physics step. That is ChargerHead's
               own method, and the reason it exists: EVERY unit in this
               game uses DISCRETE collision detection on a 0.02 second
               step, so anything moving faster than about 50 units a
               second skips a 1-unit object between steps. A boosting
               ship is exactly that fast.

               "collision" uses the stock Hazard's callbacks. Honest
               for slow contact; misses the impacts a ram is for. Use
               it to compare the two.

    radius     how wide the check is. 0 takes it from your ship's own
               collider, which is almost always right - the build log
               prints what it resolved to, since it is derived per ship
               rather than being a number anyone could look up.

    whileBoosting
               ARM IT ONLY WHILE BOOSTING. The more interesting design,
               and the game's own precedent: the ship's ImpactDamage is
               enabled by SetBoosted and off the rest of the time. A
               dash costs fuel, so a boost-gated ram is a decision
               rather than a passive. Off by default = a permanent hull
               spike.

    ignoreSelfDamage
               SUPPRESS YOUR SHIP'S OWN CRASH DAMAGE while the module
               is installed.

               Worth knowing why this is here: ImpactDamage hurts YOU
               on a hard impact and is live exactly while you boost -
               so a ram module, used the way it wants to be used, hurts
               its owner. This disables that one component rather than
               granting invulnerability (which would block everything
               else too), and RESTORES it when you pull the card. Off
               by default, because taking the crash damage is an honest
               trade.

    tint / tintPulse / tintStrength / tintMode
               a colour held on your ship while the module is live, so
               a spiked hull looks like one. Its own "contact" layer,
               so it composes with a crit flash rather than one
               restoring over the other.

  IT NEVER TOUCHES YOUR OWN SIDE - a minion you summoned sits on the
  same layer as an enemy, and ramming your own swarm is the shape that
  once made one eat itself.

  A RAM KILL IS CREDITED, so on-kill rewards fire for it - including a
  gas cloud on the corpse, which is the combination somebody will try
  first. Note the game's own hazards do NOT do this: a Larva's beak
  kill credits nobody.

  TWO CONTACT MODULES ON ONE SHIP: the HIGHEST "damage" wins and its
  push, recoil, radius, delay and tint come with it. Not summed, on
  purpose - combining them would mean choosing whose repeatDelay and
  whose radius as well, which is a resolution pass for a case nobody
  asked for. The build log says so once per run.

  NOT PORTED from Weapon Forge's version: "who": "marked" (making the
  units a weapon has touched dangerous) and "enemies" / "all" (making
  every enemy in the game dangerous). The first needs a per-hit weapon
  path and is a different feature; the second is a world rule arming
  things you do not own, which is a downside card wanting its own
  design rather than a flag on this one.


  ExecuteEffect (aliases "execute", "finish", "finisher")
     { percent, flat, stackPercent, stackFlat, maxTargetHealth,
       color, colorSeconds, colorPulse, tintStrength, tintMode, sfx }

  FINISH anything your hit leaves under a threshold. The classic
  execute: chip it low and it dies rather than limping away.

  WHOSE HITS COUNT IS DECIDED BY WHICH GRID YOU PUT IT IN, the same
  free scoping every effect here uses. In a WEAPON's grid, only that
  gun executes. On the SHIP grid, every weapon you carry does. The
  card says which.

    percent    a FRACTION of the victim's own health pool. 0.15
               finishes anything left below 15%.

               WRITE IT AS A FRACTION. A value above 1 is read as a
               percent and converted with a warning, because
               "percent": 20 means "below 2000% health" - which every
               living thing satisfies, so the module would delete
               everything it touched and read as the mod being broken
               rather than as a typo.

    flat       an ABSOLUTE amount instead of a share. Whichever of the
               two is satisfied FIRST wins, so one card can say "under
               15% OR under 20 health" and catch the chaff and the big
               one at once.

    stackPercent
               WHAT A SECOND COPY OF THIS MODULE ADDS. Each copy of this
               same module past the first adds this to "percent":
               "percent": 0.2 with "stackPercent": 0.1 is 20% for one
               card, 30% for two, 40% for three. A fraction, like
               percent (above 1 is read as a percent). 0 - the default -
               means copies do NOT stack and the strongest one counts,
               which is how every file without this key reads.
               Only copies of THIS file stack: a different execute module
               still counts on its own, strongest wins. The strongest
               copy is the base (a BoosterCore beside one raises its own
               level), the stack goes on top, and the smallest boss
               guard among the copies holds. The card shows the stack
               you are carrying ("2 COPIES  below 30% health"), and the
               build log prints what 2, 3 and 4 copies come to.

    stackFlat  the same idea for "flat": each extra copy adds this much
               health to the flat threshold. 0 = no stacking.

    maxTargetHealth
               THE BOSS GUARD, and it matters more than it looks. Skip
               anything whose health POOL is larger than this. 0 means
               no limit and the build log warns you: a 15% execute on
               a 2000-health boss is 300 free damage in a single hit,
               which is a different module than the finisher you think
               you are making.

               Deliberately NOT per-level - a cap that moves with level
               is a cap that quietly stops protecting you at the level
               you were relying on it.

    color / colorSeconds / colorPulse / tintStrength / tintMode / sfx
               the cue. THE GAME ANNOUNCES NOTHING on its own - there
               are no floating damage numbers anywhere in PUNK - so
               without one an execute is invisible and just reads as
               the enemy dying. The tint goes on its own "execute"
               layer, so an execute flash and a crit flash on the same
               frame compose rather than one restoring over the other.

  THE KILL CREDITS ITSELF, which is worth knowing because it makes
  this compose with everything: the game's own death check runs AFTER
  the damage call returns, so finishing a unit there is seen by the
  same line that credits an ordinary kill. On-kill rewards, leech, a
  gas cloud on the corpse and the music controller all fire normally.

  WHAT IT WILL NEVER EXECUTE, and each falls out rather than being a
  rule:
    - anything killed by a BURN TICK, a GAS CLOUD or a CELL - those
      report no weapon, so the threshold is never even asked.
    - anything the hit did not actually hurt. Damage is refused three
      silent ways (a damage blocker, i-frames, or the target having no
      tank of that damage type - which is how a Crawler resists nearly
      everything), and on any of them the health is untouched.
    - anything with no tank of the type you hit. That one is the
      dangerous case: its health reads 0, which looks exactly like
      "nearly dead".
    - YOURSELF or anything on your side, so a minion caught in your own
      blast is safe.

  IT DOES NOT STAND DOWN FOR WEAPON FORGE, unlike crit and leech.
  Those two have to, because two engines would each roll their own
  dice or each pay out their own healing. An execute is idempotent -
  the second one to look finds the target already dead and stops - so
  a weapon's own execute block and a module's simply both apply, which
  is what "two independent sources" should mean. The only cost is that
  which mod's colour and sound you see is arbitrary.


  GrowEffect (aliases "grow", "growth", "growingshot")
     { from, to, span, overTime, hitbox, curve, clamp }

  YOUR SHOTS CHANGE SIZE AS THEY TRAVEL - a pinprick that arrives as a
  wrecking ball, or a fat slug that tapers away to nothing.

    from       starting size as a MULTIPLIER of the shot's normal
               size, so 1 is unchanged. 0.4 launches at under half.
    to         size at the end of the ramp. Below "from" SHRINKS
               instead, which is a real weapon and not a mistake - the
               card says SHRINKS when you do it.
    span       how far (world units) or how long (seconds, with
               overTime) the ramp takes.

               LEAVE IT AT 0 for the answer you usually want: each shot
               borrows its OWN range or lifetime, so it peaks exactly
               as it runs out - whatever gun the module ends up beside,
               which a module cannot know in advance.

               Note a LOBBED shot's range is inert in this game: the
               engine computes a time from it once at launch and never
               enforces it, and every stock lobbed weapon ships it
               disabled. So a distance ramp on a grenade falls back to
               10 units.

    overTime   measure in SECONDS ALIVE instead of DISTANCE TRAVELLED.
               Distance is what "grows as it flies" usually means and
               looks right on a fast shot; time is the one for
               something that hovers, arcs or slows down.

    hitbox     DEFAULT TRUE, and this is the switch that decides
               whether this is a weapon change or a paint job.

               The game rebuilds each shot's collision sweep from its
               Radius EVERY frame, so growing that number grows the
               real damage volume - what you see and what hits are
               driven by one value, with nothing to keep in step.

               IT CANNOT BE HONOURED ON A LOBBED OR ROCKET WEAPON.
               Those collide with a real Collider2D that scales with
               the sprite, so there is no separate radius to hold
               still and the hitbox grows regardless. The build log
               says so rather than pretending.

    curve      shape of the ramp. 1 is steady. ABOVE 1 stays small and
               swells late - 3 means it is near its starting size for
               most of the flight and blows up at the end. Below 1
               swells fast then eases.
    clamp      DEFAULT TRUE, stop at "to". Off keeps it growing for as
               long as the shot lives, which on a slow or long-lived
               shot gets very large - that is the point, but know it
               before firing indoors.

  THERE IS NO DAMAGE MULTIPLIER HERE, and that is a constraint rather
  than an oversight. Weapon Forge's version can raise damage at full
  size because it publishes into a damage STACK - one captured base per
  shot, every contributor multiplied, order-independent. This mod has
  no such stack, and it already has something writing projectile damage
  in flight: a pierce module's falloff multiplies it on every target a
  shot passes through. A grow multiplier writing from its own base each
  frame would erase that falloff on the next one, and both logs would
  report success. Size and hitbox are the whole headline; the damage
  ramp needs the stack ported first.

  TWO GROW MODULES ON ONE GUN: only one ramp applies, and the build log
  says so once per run. They cannot be combined in any way you could
  predict - two 0.4-to-3 ramps multiplied would be 0.16-to-9, a
  different weapon than either, and averaging gives neither. A module
  in the WEAPON's own grid wins over one on the ship grid.


  WindupEffect (aliases "windup", "rampUp", "spool")
     { windUpTime, windDownTime, grace, ramp, steps,
       rate, fireRateAtFull, accuracy, accuracyAtFull, spreadAtFull,
       damage/damageAtFull, pellets/pelletsAtFull, cheaper/costAtFull,
       speed/speedAtFull, range/rangeAtFull, size/sizeAtFull,
       burst/burstAtFull/burstDelayAtFull, burn/burnAtFull,
       explosion/explosionAtFull, push/pushAtFull/knockbackAtFull,
       warmup/warmupAtFull, lifetime/lifetimeAtFull,
       showOnHud, readySfx, stepSfx, lostSfx }

  HOLD THE TRIGGER AND THE GUN GETS BETTER. The mirror of an overheat:
  instead of degrading as you lean on it, it winds up.

  *** IT IS NOT CALLED "spinUp" HERE, AND THAT IS ON PURPOSE. ***
  Weapon Forge calls this exact feature "spinUp". In THIS mod that word
  was already taken before this existed: "type": "spinup" is an alias
  on ExtraWeaponStatEffect pointing at the game's own "warmupTime" -
  the flat delay before a gun starts firing, one number, applied once,
  no meter and no reward. Writing "spinup" in a module still gets you
  that, and the build log now warns and points here. The two mods
  spell one idea two ways because the collision was real; everywhere
  else they agree deliberately.

    windUpTime   SECONDS OF SUSTAINED FIRE to reach full.

                 What counts as firing is the game's own definition -
                 the trigger is down, you can afford the shots, and
                 nothing is blocking the gun. So an EMPTY GUN DOES NOT
                 WIND UP, and a jam or a stun costs you the wind-up you
                 had. That falls out of the definition rather than
                 being a special case.

                 Per level, and like slow's "amount" THE PER-LEVEL BOX
                 WANTS A NEGATIVE NUMBER, since getting there faster is
                 a smaller number. -1 or -2 is fine.

                 IT IS FLOORED AT 0 AND NEVER GOES NEGATIVE, and at 0
                 the gun is fully wound from the first shot - a
                 different module, with no ramp left to feel. That is
                 reachable by ordinary numbers rather than by typing
                 0: base 2 with -1 per level is 2s, 1s, then ZERO at
                 level 3, which one BoosterCore can reach. The build
                 log works out that level and names it, and the card
                 reads "instant - full from the first shot" rather
                 than "0s of firing".

    windDownTime seconds to fall back to nothing once you stop. The
                 rewards are withdrawn as it falls, so the gun is
                 handed back gradually. Pulling the module out of the
                 grid runs this same wind-down rather than cutting.
    grace        seconds off the trigger before the wind-down even
                 starts - the trigger-discipline knob. Without it,
                 tapping keeps the bonus for free.
    ramp         "smooth" (default), "stepped" or "click".

                 stepped awards the reward in whole stages, each one
                 announced by stepSfx - pick it if you want the player
                 to feel a threshold. click is smooth but holds the cue
                 back so reaching FULL is a moment you can hear.
    steps        how many stages in stepped mode. 1 is the same as
                 smooth and the log says so.

  THE REWARDS - each is a switch plus its own "at full" multiplier,
  and all seventeen are the same set the weapon side pays:

    rate         DEFAULT ON. x2 fire rate at full by default. The game
                 recomputes the gap between shots fresh every frame, so
                 this shortens the gap you are ALREADY waiting through.
    accuracy     DEFAULT ON. Tightens the random scatter.

                 *** MOST STOCK WEAPONS SHIP angleVariance AT ZERO ***
                 - Popper, Shotgun, Bolt, Worm - so on those there is
                 nothing to remove and you will see no change. The
                 build log says so. A shotgun's fan is "spread", a
                 different field, left alone unless you set
                 spreadAtFull (below 1 tightens it, which turns a
                 shotgun into a slug gun - the point, or a surprise).

                 accuracyAtFull is the FRACTION OF SCATTER REMOVED, so
                 1 is pinpoint and 0.5 halves it.

    damage, pellets, cheaper, speed, range, size, burst, burn,
    explosion, push, warmup, lifetime
                 all off by default, all the same shape. Notes worth
                 having: pellets rebuilds the weapon's visuals on every
                 whole-number change (a BEAM indexes its visual list
                 with no bounds check every frame, so a count that rose
                 behind its back would throw sixty times a second);
                 size grows the real HITBOX, not just the art;
                 explosion scales radius AND damage together; and
                 knockbackAtFull is YOUR recoil, left at 1 because
                 being shoved harder is a cost unless you meant it.

  FEEDBACK
    showOnHud    DEFAULT ON - a WOUND UP readout with the percentage,
                 through this mod's buff indicator.

                 *** THERE IS NO MUZZLE TINT HERE *** unlike the
                 weapon-side version, which colours the muzzle flash as
                 the meter fills. That rides a muzzle-flash layer table
                 this mod does not have, and building one is its own
                 job. The HUD readout is arguably the better fit
                 anyway: a module applies to every gun you carry, so a
                 per-weapon muzzle colour would be the more ambiguous
                 signal.

    readySfx     plays the moment it reaches full.
    stepSfx      plays on each step crossed, in stepped mode.
    lostSfx      plays when a fully wound gun has wound all the way
                 back down - so losing it is something you notice
                 rather than something you discover.

  *** GADGET WEAPONS CANNOT BE REACHED. *** The meter is driven by the
  held trigger, and gadgets fire directly without ever touching the
  trigger machinery - so a windup module beside a gadget does nothing.
  The weapon-side version REFUSES a gadget at build time and says so,
  because a weapon file names its own slot. A module cannot: you choose
  the slot, so there is no build-time moment at which the question can
  be asked. Instead the card says "Needs: a held trigger (not gadgets)"
  and the log warns the first time such a weapon fires.

  WHICH GRID DECIDES THE SCOPE, free, as with crit, execute and slow:
  in a WEAPON's grid only that gun winds up; on the SHIP grid every
  weapon does. The card says which.

  TWO WINDUP MODULES: only one ramp applies, and the one in the
  weapon's own grid wins. They cannot be combined in any way you could
  predict - two ramps multiplied would be a third weapon that is
  neither, and averaging their times describes neither card. Same
  answer as two grow modules, for the same reason.

  WITH WEAPON FORGE INSTALLED, a weapon's own "spinUp" block and this
  module BOTH apply and MULTIPLY, which is correct rather than a
  conflict: both publish into one table that keeps a single captured
  base per stat and multiplies the named contributors. No coordination
  was needed beyond making sure the two use different names for their
  contributions - which the rename gave for free.


  SlowEffect (aliases "slow", "chill", "timeSlow", "hitStop")
     { amount, duration, mode, floor, maxStacks, cooldown,
       slowMove, slowTurn, slowFire, slowShots, slowKnockback,
       tint, tintStrength, tintMode,
       timeSlow, timeScale, timeDuration, timeCooldown,
       timeEase, timeUnscaled, timeMode, onHit, onKill, debuff }

  TWO SEPARATE THINGS THAT BOTH MAKE A HIT LAND, in one block because
  they are usually wanted together:

    the DEBUFF     cripples the thing you hit. You stay at full speed.
    the TIME BEND  slows EVERYTHING for a moment, you included -
                   hit-stop. It needs no victim at all.

  They share no mechanism, and either works without the other.

  -- THE DEBUFF ------------------------------------------------------

    amount     THE TARGET FRACTION OF NORMAL SPEED, so LOWER IS
               STRONGER. 0.5 is half speed, 0.2 is a crawl, 1 is
               nothing. A value above 1 is read as a percent and
               converted with a warning - "amount": 50 would otherwise
               mean fifty times normal speed, a speed-up module.

               PER LEVEL, and THIS IS THE ONE SERIES ON THE PAGE WHOSE
               "per level" BOX WANTS A NEGATIVE NUMBER, because a
               stronger slow is a smaller number.

    duration   seconds it lasts. Floored at 0.05. Unlike timeDuration
               below, 0 here does NOT mean forever.
    mode       what a SECOND hit on an already-slowed target does.
               "refresh" (default) resets the timer. "stack" slows
               harder each time - the amount is raised to the power of
               the stack count, so two stacks of 0.5 is 0.25 - down to
               "floor". "ignore" lets the first hit run out untouched.
    floor      THE STRONGEST A STACK CAN EVER GET, so it has to be
               BELOW "amount". The real factor is max(amount, floor),
               so "amount": 0.1 with the default floor of 0.2 is
               really a 20% slow wearing a 10% label. The build log
               warns when they are the wrong way round.
    maxStacks  how many times "stack" can compound. 1 behaves exactly
               like refresh and the log says so.
    cooldown   seconds before the same target can be re-slowed at all.
               0 (default) is usually right - the factor is recomputed
               from the ORIGINAL each time rather than compounded, so
               a piercing beam re-slowing every tick costs nothing.

    slowMove       DEFAULT TRUE - how fast it travels.
    slowTurn       DEFAULT TRUE - how fast it turns to face you. Most
                   of what makes a slow feel like a slow.
    slowFire       DEFAULT TRUE - the victim's own fire rate.
    slowShots      DEFAULT TRUE, and the half you can actually see:
                   slowFire changes how OFTEN it shoots, this changes
                   how FAST THE BULLETS TRAVEL, so you can dodge them.
    slowKnockback  DEFAULT TRUE - makes it LIGHTER, so your shots and
                   blasts throw it further. Its own locomotion is
                   unaffected.

    tint, tintStrength, tintMode
               a colour held on the victim for as long as it is
               slowed, cleared when the debuff expires rather than
               timed separately so it cannot flicker off mid-slow.
               Multiply can only darken; neither mode can brighten
               dark art, so pick a saturated colour.

  WHY IT TOUCHES THE RIGIDBODY AND NOT THE MOVEMENT SETTINGS, because
  it explains the shape of every knob above. A unit carries one
  movement component PER AI STATE, and the game snapshots that
  component's values when a state begins and restores them wholesale
  when it ends. A slow written there is reverted at the next state
  change - and, worse, if a state happens to BEGIN while the unit is
  slowed, the slowed numbers become that state's "original" and are
  restored forever after. A temporary debuff would become PERMANENT,
  at random, depending on AI timing. Nothing snapshots the rigidbody,
  so movement is its linear damping, turning its angular damping,
  and knockback its mass.

  -- THE TIME BEND ---------------------------------------------------

    timeSlow       turn it on. Set automatically if you give a
                   timeScale, so you rarely need this key.
    timeScale      how slow time runs - 0.35 is a third speed. The
                   game takes the STRONGEST live bend rather than
                   compounding them, so overlapping ones cannot run
                   away.
    timeDuration   how long, in REAL seconds.

                   *** 0 OR LESS MEANS FOREVER IN THIS GAME. ***
                   The engine treats a non-positive duration as
                   indefinite and never checks it for expiry, so it
                   would hold the whole game in slow motion for the
                   rest of the run. Clamped to 0.01 with a warning,
                   but do not rely on that.

    timeCooldown   the least time between two bends.

                   *** SET THIS ON A SHIP-GRID MODULE. *** A module
                   applies to every gun it is connected to, so on the
                   ship grid this fires on every hit from EVERY weapon
                   you carry - and a beam or a shotgun re-triggers it
                   several times a second, which reads as the game
                   stuttering rather than punching. The weapon version
                   never had this problem, because a weapon's timeSlow
                   only ever fires for that weapon. About 1 is a good
                   start, or use onKill instead. The build log warns
                   when there is no cooldown at all.

    timeEase       DEFAULT TRUE - ride back up to normal across the
                   duration instead of snapping. Most of what makes
                   hit-stop feel good.
    timeUnscaled   DEFAULT TRUE and you want it. With it off the
                   engine measures the bend with the clock it has just
                   slowed, so a 0.25s bend at scale 0.2 really lasts
                   1.25 seconds - and the heavier the slow the further
                   it overruns.
    timeMode       only "ignore" means anything: it drops a new bend
                   while one is still running.

  -- BOTH ------------------------------------------------------------

    onHit      DEFAULT TRUE - fire on every hit that connects.
    onKill     also fire when the hit KILLS. Independent triggers, so
               a card can do a small debuff on every hit and save the
               time bend for the kill - the combination worth trying
               first, since it needs no cooldown. A dead thing is not
               debuffed (there is nothing left to slow), so on a kill
               this means the time bend.
    debuff     DEFAULT TRUE. Off makes a pure hit-stop module. The
               build log refuses a card with this off and no timeSlow.

  WHICH GRID DECIDES THE SCOPE, free, as with crit and execute: in a
  WEAPON's grid only that gun slows; on the SHIP grid every weapon
  does. The card says which. It never touches you or your own side.

  DAMAGE OVER TIME CANNOT SLOW. Burn ticks, cell damage and a gas
  cloud's damage reach the game by a different route and report no
  weapon at all, so there is nothing for a module to match against.
  That falls out of how kills are attributed rather than being a rule.

  TWO SLOW MODULES: the STRONGEST wins, per half, and the two halves
  are resolved separately - so a card carrying only a debuff and a
  card carrying only a time bend both apply. Ties are broken by the
  longer duration, so the answer never depends on which card you
  placed first. They are not added: two halving modules are not a
  total stop in any sense you could predict.

  *** "slow" IS ALSO A KEY INSIDE THE GAS BLOCK, AND IT IS A
  DIFFERENT THING. *** KillRewardEffect's "gas.slow" is a per-tick
  velocity drag applied to anything standing in the cloud - no
  duration, no restore, no fire-rate change. Weapon Forge spells both
  the same way, so the two mods agree, but one word covering two
  mechanisms is worth knowing before you go looking for the wrong one.

  WITH WEAPON FORGE INSTALLED, that mod owns the debuff and a slow
  module's settings are applied through its engine - the build log
  says so. This is not a limitation, it is the only arrangement that
  works: both mods' live debuffs remember the victim's ORIGINAL speed
  and weight, so with two of them the second to arrive remembers the
  already-slowed numbers and restores to THOSE. The enemy would stay
  crippled for the rest of the run, with both mods reporting a correct
  restore. The TIME BEND still runs here whichever mods are installed,
  because the game's own time manager takes the strongest live bend
  and so arbitrates for us.


  CritEffect (alias "crit")
     { chance, multiplierBonus, roll, overflow,
       impact, impactScale, color, colorSeconds, colorPulse,
       tintStrength, sfx, shake }

  A chance for your hits to do MULTIPLIED damage.

    { "type": "crit", "chance": 0.15 }

  is the whole minimum: 15% of hits do double damage.

  WHICH GRID DECIDES THE SCOPE, exactly as it does for onKill above,
  and again you do not set a flag:
     on the SHIP grid    -> EVERY weapon crits
     in a WEAPON's grid  -> only THAT weapon crits
  The module's card says which ("Applies to: this weapon" / "every
  weapon").

  A CRIT IS INVISIBLE UNLESS YOU ASK FOR A CUE. This game has no
  floating damage numbers anywhere - no DamageNumber, no FloatingText,
  nothing. That is why "impact" defaults ON: it is the one cue that
  needs no work from you. Switch them all off and the build log warns
  you.

    chance     0.15 = 15%. A number ABOVE 1 is read as a percent and
               converted (15 becomes 0.15), because "always crit,
               fifteen stacks deep" is not something anyone types on
               purpose - the log says when it guesses. A series, so a
               level can buy RELIABILITY rather than size.

    multiplierBonus
               ADDED to the x2 a crit already does, so 0.5 means x2.5
               and 0 means a plain double-damage crit.

               IT IS NOT CALLED "multiplier" ON PURPOSE. On a WEAPON
               (Weapon Forge's "crit" block) that word is the ABSOLUTE,
               where 2 means double. The same word meaning two things
               would be a trap - somebody writing "multiplier": 2 here
               would get x4 with no warning - so a module uses this word
               and the build log rejects the other one out loud.

               A module with a bonus and NO chance is legitimate and
               does nothing on its own: it makes the crits you get from
               a weapon or another module hit harder. The log notes it
               in case that was not the intent.

    roll       WHEN THE DICE ARE ROLLED. Three modes:
                 "hit"   once per thing damaged, so a piercing shot
                         rolls again for each enemy. The default, and
                         the only mode that means anything on a BEAM or
                         an EXPLOSION.
                 "shot"  once per projectile - a SHOTGUN rolls per
                         PELLET, and a pellet that crits crits
                         everything it touches.
                 "pull"  once per trigger pull, so a whole blast crits
                         together or not at all. Built because "half my
                         pellets crit" reads as noise rather than as a
                         payoff.

    overflow   default TRUE. Above 100% the excess becomes a chance at a
               SECOND crit stack instead of being thrown away: 1.5
               always crits and half the time crits twice.
               STACKS ADD THE BONUS, so two stacks of x2 is x3, not x4 -
               multiplying would make three stacks x8 and stop being
               tunable. Hard-capped at 8 stacks, so a pile of modules
               gone wrong cannot silently produce a 40x hit.

    impact / impactScale
               a second, LARGER copy of the weapon's own impact burst.
               On by default. PROJECTILE HITS ONLY - a beam's spark and
               an explosion's flash are not per-hit prefabs to borrow,
               so use colour / sound / shake for those. The log says so
               once if a crit lands by another route.

    color / colorSeconds / colorPulse
               a brief tint on whatever got crit - a game colour name or
               #hex. It goes through the tint owner, which keeps ONE
               captured base colour per sprite and multiplies live
               layers over it, so it can never bake a colour in
               permanently the way a save-and-restore tint does.

    tintStrength
               HOW HARD THAT COLOUR COMES THROUGH, 0 to 1. 1 is the full
               colour and is what this has always done; 0.35 is a hint
               of it; 0 is no tint at all. Either spelling is accepted
               ("tintStrength" or "colorStrength"), because this mod's
               blocks are split between color* and tint* naming and
               remembering which prefix a given block uses is a bug
               generator.

               It MULTIPLIES the pulse rather than replacing it, so a
               half-strength pulsing tint still pulses - between
               "nothing" and "half" rather than between "nothing" and
               "full".

               Worth turning down when several effects tint the same
               unit: live layers MULTIPLY, so two full-strength colours
               read as very dark. That compounding is deliberate - it is
               what makes stacked debuffs legible - but it is a lot.

    tintMode   "multiply" (the default) or "replace".

               IF YOU HAVE TURNED THE STRENGTH UP AND IT STILL IS NOT
               OBVIOUS, THIS IS THE KNOB YOU WANT. A multiply can ONLY
               DARKEN - your colour is multiplied into the sprite's own,
               so it moves the pixel toward black and never toward the
               colour. A pale flash over a dark grey Cross barely
               registers while the same flash over a pale Fly reads
               clearly, which is the "some enemies look tinted and
               others not so much" report. And no strength value fixes
               it: at 1 a multiply is already as strong as a multiply
               gets.

               "replace" stops your colour COMPOUNDING - it sets the
               tint factor to your colour rather than multiplying it
               into whatever the prefab and the other live layers
               already put there, so it is the strongest a tint can be.
               Reach for it when the tint is a READOUT you need to spot
               in a fight.

               BUT NEITHER MODE CAN BRIGHTEN DARK ART. A sprite's
               colour is a VERTEX MULTIPLY IN THE SHADER, so the pixel
               you see is always "texture x colour" and the most any
               tint can do is "texel x yours". The Fly's body art
               averages 40/255 luminance - 16% grey - against 76 for
               its beak, which is why a crit flash reads on the mouth
               and barely on the body. Pick a colour that survives a
               multiply (saturated reds, oranges, greens - not pale
               pastels), or use "colorPulse", since motion is visible
               at any brightness.

                   "tintMode": "replace", "tintStrength": 0.8

               "colorMode" is accepted as a spelling of the key, and
               "tint" as a spelling of multiply - Weapon Forge's minion
               "colorMode" already calls the same two things "replace"
               and "tint", and two vocabularies for one idea across the
               two mods is a bug report waiting to happen.

               Multiply resolves first and replace paints over the
               result; two replace layers average rather than
               overwriting.

               WITH WEAPON FORGE INSTALLED that mod owns the crit patch,
               so the LOOK comes from the weapon's own "crit" block and
               this is announced rather than applied. Set it on the
               weapon instead; the build log says so once per run. Weapon
               Forge takes the same key on nine different blocks.

    sfx        a distinct sound. Use the READABLE NAME of any of the
               game's own sounds - "Cells/Fuel", "UI/OK",
               "Weapons/Popper/Shoot" - all 259 are listed in
               SOUNDS.txt next to this file. A raw sound id still
               works. Or the name of a CUSTOM sound - but custom
               sounds live in Weapon Forge's "sounds" folder and only
               resolve with that mod installed
               (one folder and one set of names across both mods, rather
               than a second decoder here). A name nothing knows is
               reported in the log rather than being silently mute.

    shake      kick the camera, using the WEAPON's own shake preset - so
               it shakes like a heavier version of that gun rather than
               a generic thump. Off by default; crit-per-hit with shake
               on is a lot of camera.

  WHERE THE NUMBERS SHOW UP
  Hovering the MODULE shows what THAT module contributes, its scope and
  its cues. Hovering the WEAPON shows ONE combined "CRIT 15% X2.5" line
  for everything in force on that gun.

  WITH WEAPON FORGE INSTALLED, IT OWNS THE CRIT. Both mods can crit,
  and a crit is a patch on the game's one damage method - two of them
  would each roll their own dice on the same hit, so a player with both
  mods would get roughly double the crit rate they asked for and two
  impact bursts stacked on each other. So there is exactly one owner,
  the same bargain as the burn engine with the sides swapped:

     Weapon Forge installed  -> it owns the crit patch. This module's
                                CHANCE and MULTIPLIER are added to the
                                weapon's own, giving one number; the
                                LOOK (roll mode and the four cues) comes
                                from that weapon's "crit" block, or from
                                its defaults. The log says this once.
     Weapon Forge absent     -> this mod runs its own crit engine and
                                everything above applies as written.

  Nothing is lost either way - with both mods, set the look on the
  weapon and the chance on the module.

  FREE CUE WITH WEAPON FORGE: a weapon with
  "hitSound": { "pitch": "damage" } already pitches its hit tick by the
  damage dealt, so a crit sounds heavier with no "sfx" set at all.

  70 OF THE 259 ARE DECLARED WITH NO CLIP AT ALL. They resolve

  LeechEffect (alias "leech", "lifesteal")
     { fraction, flat, maxPerSecond, perEnemyDelay, resource, healOn,
       orb, orbSprite, orbFps, orbScale, orbSpeed, orbArc, orbSpin,
       orbLifetime, orbColor, maxOrbs, sfx }

  YOUR HITS HEAL YOU.

    { "type": "leech", "fraction": 0.15, "maxPerSecond": 4 }

  WHICH GRID DECIDES THE SCOPE, same as onKill and crit above:
     on the SHIP grid    -> EVERY weapon drains
     in a WEAPON's grid  -> only THAT weapon drains
  The card says which ("Applies to: this weapon" / "every weapon").

  IT ONLY PAYS FOR DAMAGE THAT LANDED, and this is the finding the whole
  effect is built on. The game's own Damage() refuses a hit three silent
  ways before it ever touches a tank:

      invincibility (damageBlockers)
      i-frames (iFrameDuration)
      the enemy having NO TANK of that damage type at all

  The last one is not a corner case - it is how a Crawler resists nearly
  every damage type. So this measures the enemy's own health pool before
  and after the hit rather than reading the damage number. Reading the
  number would have healed you for hits that did nothing, and you would
  have found out as "leech is overpowered against Crawlers".

  OVERKILL DOES NOT PAY. A 200-damage rocket into a 5-health fly leeches
  off 5. (The game writes health as `tank.Value -= amount` with no
  floor, so the raw difference there would read 200.)

  BURN AND TERRAIN DAMAGE NEVER LEECH. They report no weapon, so there
  is nothing to credit and they are excluded for free.

    fraction   share of the damage you dealt. 0.15 = 15%. A series, so a
               level can buy the share.

               NOT AUTO-CORRECTED FROM A PERCENT, unlike crit's
               "chance". Healing for more than you dealt is a legitimate
               build, so dividing by 100 would put it out of reach - 15
               means 1500% and the log says so loudly enough to catch a
               typo on the first shot.

    flat       a fixed amount per hit whatever the damage was. Stacks
               with the share; either alone is a complete module. Good
               on a weak, fast weapon where a share rounds to nothing.

    maxPerSecond
               THE NUMBER THAT DECIDES WHETHER THIS IS BALANCED, and it
               matters MORE on a module than on a weapon. A BEAM damages
               its target every damageRepeatDelay (0.08s on the stock
               Caps Laser) and a piercing one does that to every enemy
               it threads - roughly 75 heals a second through six
               enemies. On the SHIP grid this module applies to every
               weapon you carry, so it can find that beam without you
               planning it. 0 = uncapped, and the log warns.

               PARTIAL, not all-or-nothing: a hit that wants 3 with 2
               left in the budget heals 2. An all-or-nothing cap makes a
               weapon feel randomly dead.

               A series, so a level can buy SUSTAIN - the more
               interesting of the two dials on a leech module.

    perEnemyDelay
               seconds before the SAME enemy can feed you again. 0 =
               off. A different flavour of limit: it rewards spreading
               damage across a crowd rather than focusing one target.
               Use both if you like.

    resource   which pool refills. LEAVE IT BLANK almost always - blank
               means your ship's own health pool, read off the ship
               itself rather than guessed from the name "Health", so
               there is nothing to spell wrong. Name a resource for an
               ammo-leech or a fuel-leech instead.

    healOn     "arrival" (default) or "hit".

               arrival: the health lands when the bubble reaches your
               ship, so it reads as absorption rather than as a number
               changing. Costs a fraction of a second.

               hit: instant and predictable - the one for a module that
               wants the drain without the flourish.

               AN ORB THAT CANNOT REACH YOU PAYS OUT ANYWAY after
               orbLifetime; a lost orb would be lost HEALING, which is
               the worst way this could fail. And with "orb": false this
               falls back to "hit" by itself, because otherwise it would
               heal never.

  THE ABSORB ORB
  --------------

  A bubble that leaves the enemy and flies into your ship.

  IT IS NOT A WEAPON AND NOT A PROJECTILE - a bare object with a sprite:
  no collider, no faction, no damage, invisible to every projectile
  feature in either mod. It TRACKS your ship as it flies, because a
  fixed heading means a moving player outruns their own healing.

    orb          default true. Off makes leech invisible and fully
                 functional, and switches healOn to "hit" by itself.
    orbSprite    default "area_zero_particle_tuff" - the bubbles from a
                 white tuff block, all nine frames, animated.

                 NAMING THE BASE ANIMATES; NAMING A FRAME DOES NOT.
                 "area_zero_particle_tuff" plays _0 through _8 as a
                 flipbook; "area_zero_particle_tuff_0" is that one
                 frozen frame. The rule is that way round so nothing
                 already written changes look - "part_cyrcle_12" has to
                 keep meaning frame 12 rather than animating through the
                 whole set.

                 GAME SPRITES ONLY here. Custom PNGs live in Weapon
                 Forge's sprites folder, and when that mod is installed
                 IT owns the orb anyway. An unknown name falls back to
                 the game's white-block orb rather than to no orb.

                 THE NAME CAN ALSO PICK FRAMES, same syntax as Weapon
                 Forge so there is one vocabulary across both mods:

                   area_zero_particle_tuff        every frame
                   area_zero_particle_tuff:2-6    frames 2 to 6
                   area_zero_particle_tuff:8-0    REVERSED
                   area_zero_particle_tuff:0,3,5  those three, in order
                   area_zero_particle_tuff:4      one frozen frame

                 Frame numbers are 0-based, and on a stock run the
                 number IS the one in the sprite's name. A number
                 outside the animation is reported and skipped.

                 SPEED IS NOT IN THE NAME HERE - use "orbFps". Weapon
                 Forge accepts an "@24" suffix because several of its
                 sprite keys have no fps of their own; the orb does, so
                 an "@" here warns and points at the key rather than
                 being two ways to say one thing.
    orbFps       animation speed, default 14.
    orbScale     size multiplier, default 1. The tuff bubbles are
                 particle art and small; try 1.5-2 if they read as
                 specks.
    orbSpeed     units per second, default 22.
    orbArc       how much it SWOOPS instead of beelining, as a share of
                 its speed thrown sideways at launch. Default 0.7; 0 is
                 a straight line. Worth keeping above zero - a
                 dead-straight line reads as a bullet being fired AT
                 you, which is the one thing this must not look like.
    orbSpin      degrees per second, default 0.
    orbLifetime  seconds before an orb gives up, PAYS OUT ANYWAY and
                 vanishes. Default 2.5. A backstop, not a dial.
    orbColor     tint the bubble. Blank keeps the sprite's colours.
    maxOrbs      most alive at once, default 14. A shotgun with eight
                 pellets, or a beam threading a crowd, would otherwise
                 be a firehose. OVER THE CAP THE HEALING IS GRANTED
                 IMMEDIATELY rather than dropped.
    sfx          plays when the health arrives. A game sound NAME
                 from SOUNDS.txt, a sound id, or a custom name.

  WITH WEAPON FORGE INSTALLED, IT OWNS THE LEECH
  ----------------------------------------------

  Both mods can leech, and a leech is a prefix/postfix pair on the
  game's one damage method. Two of them would each measure the same hit
  and each pay out - so a player with both mods would heal roughly twice
  what they asked for and see two bubbles per hit. So there is exactly
  one owner, the same bargain as crit and the mirror of the burn engine:

     Weapon Forge installed  -> it owns the patch. This module's SHARE,
                                FLAT amount and CAP are combined with
                                the weapon's own; WHEN the heal lands,
                                the orb's look and which pool refills
                                come from that weapon's "leech" block
                                (or its defaults). The log says so once.
     Weapon Forge absent     -> this mod runs its own leech engine and
                                everything above applies as written.

  THE CAP CROSSES THE BRIDGE ON PURPOSE and it is the safety valve: the
  TIGHTEST cap wins between the module and the weapon, so a cap you set
  here is never overridden by a weapon whose author left it uncapped.
  Same for perEnemyDelay, where the LONGEST wait wins.

  Nothing is lost either way - with both mods, set the look on the
  weapon and the numbers on the module.

  ShipStatEffect { targetProperty, operation, deltaCalculationMode,
                   value }
     HOW THE SHIP HANDLES - the surface the game's own modules cannot
     touch at all. Not one of its eleven effect classes references
     ShipMovement or DamagableResource.

       { "type": "dash", "targetProperty": "DashCooldown",
         "value": -0.3 }

     targetProperty:
       MaxSpeed        top speed
       Acceleration    how fast you get there
       DashCost        fuel per dash
       DashCooldown    seconds between dashes
       DashDuration    how long a dash lasts
       DashForce       the initial kick        (one-shot, 400)
       DashPush        the sustained push      (whole dash, 500)
       IFrames         the gap between hits that can damage you
       FuelCost        fuel per second while flying
       BoostFuelCost   fuel per second while sprinting
       BoostDelay      how long you hold before a sprint starts
       BoostKick       the SPRINT BURST multiplier   (x3)
       BoostKickCap    the ceiling it can reach      (25)

       --- THE SHIP'S OWN FIRE RESISTANCE ---
       FireCooling     burn shed per second        (higher is better)
       FireTickRate    SECONDS between burn ticks  (higher is better)
       FireThreshold   burn needed to ignite       (higher is better)
       FireDamage      damage per burn tick        (LOWER is better)
       MaxBurn         how high burn can stack     (LOWER is better)
       IgniteSpike     burn added on catching fire (LOWER is better)

     Shortcut types: "speed", "engine", "dash", "iframes".

     THE DASH HAS TWO FORCES, NOT ONE. DashForce is the one-shot impulse
     at the instant the dash begins (400). DashPush is applied EVERY
     frame for the whole DashDuration (500 over 0.07s). Lengthening
     DashDuration makes DashPush matter more and DashForce matter less.

     THE SPRINT KICK IS A MULTIPLY, NOT A SPEED, and this is the part
     that surprises people. StartBoosting does:

         magnitude = velocity.magnitude
         if (magnitude < boostExtraSpeedLimit)
             velocity = min(boostExtraSpeedLimit,
                            magnitude * boostExtraSpeedMultiplier)
                        * velocity.normalized

     Three things follow, and the first is the one nobody guesses:

       - A STANDING START GETS NO KICK AT ALL. Zero times three is
         zero. The burst rewards sprinting while already moving, which
         is why it reads as a gear change and not a launch.
       - IT DOES NOTHING once you are at or above BoostKickCap, because
         of the "<" guard. So raising BoostKick without raising
         BoostKickCap buys you nothing above cap/multiplier - about 8.3
         units/second at the factory values.
       - It preserves DIRECTION, so it is purely a speed event.

     The ship's numbers: multiplier 3, cap 25, cruising maxSpeed 12.5,
     maxSpeedWhileBoosted 19. So a sprint from cruising speed asks for
     37.5, is capped to 25, and drag then pulls you back to 19. The
     burst is real and deliberately temporary.

     BoostKick is FLOORED AT 1. Below that a sprint would BRAKE you,
     and at 0 it would stop the ship dead the instant you hit sprint -
     the game applies it as an outright velocity write, not a force. 1
     already means "no kick", which is a fair downgrade to sell.

     FIRE RESISTANCE IS A DIFFERENT THING FROM EVERY OTHER BURN FEATURE
     IN THIS MOD. Those are about the burn you INFLICT. These six are
     how fast YOU stop burning and how much it hurts while you do, and
     nothing in the game's own module system touches them.

     The ship's factory values, which are worth knowing before tuning:

         fireThreshold 10   extraBurnLevelWhenCatchingFire 5
         coolingSpeed 5     fireTickRate 1
         fireDmgPerTick 1   maxBurnLevel 20

     Read that as: burn stacks up to 20; you IGNITE above 10; igniting
     instantly adds 5 more (so crossing 10 puts you at 15); you shed 5
     a second; and while alight you take 1 damage a second. A single
     ignition therefore burns for about a second - it is sustained
     exposure that hurts, not one touch.

     TAKE MaxBurn TO 10 OR BELOW AND THE SHIP CAN NEVER CATCH FIRE.
     Burn is clamped to maxBurnLevel, so a ceiling at or under the
     ignition threshold means the threshold is never crossed. That is
     a real "asbestos hull" module rather than a bug, but it is total
     immunity and worth knowing you have built one.

     FireTickRate IS AN INTERVAL, NOT A RATE, whatever the name reads
     like - it is the gap in seconds between damage ticks, so a bigger
     number burns you LESS often. Floored at 0.02s, because 0 would
     mean "tick every frame" - fifty times a second - which is the
     opposite of what anyone setting it to zero was reaching for.

     ONE MORE WRITER TO KNOW ABOUT. This mod's burn engine also writes
     fireTickRate, every frame, from a prefix on
     DamagableResource.Update. The two coordinate rather than fight: a
     fire-resistance module OWNS the value, and the burn engine treats
     it as the base it boosts from. Without that the module would
     appear to do nothing at all.

     THE FIRE STATS ARE RE-ASSERTED EVERY FRAME, deliberately, and the
     other ship stats are not. Unit.CreateData() rebuilds
     burnProperties from the prefab on spawn AND on continue, so a
     value stamped once at install is silently reverted on reload -
     the same trap that had minion colour and scale broken from the day
     they shipped.

     ON COSTS AND DELAYS, A NEGATIVE VALUE IS THE UPGRADE - DashCost,
     DashCooldown, FuelCost, BoostFuelCost and BoostDelay are all
     "less is better". The build log reminds you when you use one.

     MaxSpeed and Acceleration MOVE THEIR BOOSTED TWINS TOO, in
     proportion. This is not a nicety: ShipMovement.MaxSpeed is a
     get-only property that returns maxSpeed OR maxSpeedWhileBoosted
     depending on whether you are sprinting, so a module that changed
     only one half would appear to stop working the moment you held the
     dash button.

     IFRAMES IS 0 ON EVERY DAMAGEABLE THING IN THE GAME, so any value
     is a pure upgrade with no existing balance to preserve. It applies
     to every DamagableResource on the ship, not just health, because a
     unit has one per resource it can lose.

     WHY THESE ARE SAFE TO REMOVE, which weapon stats get for free and
     these do not: a weapon is rebuilt from its template whenever the
     module cluster changes, so a weapon effect can write
     "current + delta" and let the rebuild clean up. NOTHING rebuilds
     ShipMovement - its fields are live and permanent. Writing
     "current + delta" there would compound on every stat
     recalculation and never come back when the module was removed. So
     the mod captures the factory value once and RECOMPUTES the total
     from it, which makes removal exact even with several modules on
     the same stat, and makes a double recalculation harmless.

  InvulnEffect { seconds }
     MERCY INVINCIBILITY: total immunity for a moment after any hit.

       { "type": "invuln", "seconds": 0.75 }

     Not the same as IFrames above, though they look interchangeable:
       IFrames  rate-limits damage to ONE resource pool
       invuln   blocks EVERYTHING, on every pool, for the window
     It uses the game's own switch (DamagableResource.damageBlockers),
     not a mod-invented one.

     IT DOES NOT STACK ACROSS MODULES. Two one-second modules give one
     second, not two - the longest request wins. Immunity windows gain
     value far faster than they add, and stacking is how three cheap
     cards quietly become permanent invulnerability.

  CellConvertEffect { into, convert, radius }
     Aliases: "cellconvert", "terraform", "dig".

     YOUR WEAPON REWRITES THE TERRAIN IT HITS.

       { "type": "dig", "radius": 3 }
       { "type": "terraform", "into": "Hazard", "convert": "Solid" }

     into     what the terrain BECOMES. Defaults to "Fog Mist".
              A SINGLE TYPE - it cannot be a list. One shot turns
              terrain into ONE thing; that is the field's type in the
              game, not a limit of this mod.
     convert  which terrain it may eat. BLANK = every solid type.
     radius   how big a patch, per hit. The Crawler Laser uses 4.

     FOUR GROUP WORDS SAVE NAMING SIXTEEN THINGS. "convert" takes a
     list, a single name, or one of:

         "all"        every cell type (16)
         "solid"      everything you cannot fly through (12)
         "resources"  Tuff + Blob + Gold - A MINING MODULE
         "soft"       Slime and the three Fogs

     The same words work in Weapon Forge's "convertableCells", so
     there is one vocabulary across both mods. The log prints the full
     list it expanded to.

     THE SIXTEEN CELL TYPES. The COLLIDER column is the one that
     decides what the module feels like. You can drop the "CellType"
     prefix - "Solid", "Fog Mist" and "Slime" all resolve.

       SOLID - a wall you cannot fly through
         Bark      burns 4s
         Gold      the ore
         Blob      burns 2s
         Moss      burns 2s
         Night     burns 3s
         Shard
         Solid     burns 15s - the most flammable thing in the game
         Tuff
         Panel
         Obsidian
         Mud
         Hazard    solid AND 1 contact damage, 10 pushback

       PASSABLE - you fly straight through
         Slime          a trigger collider - passable goo
         Fog Mist       no collider at all
         Fog Musk       no collider at all
         Fog Steam      no collider at all

     SO THIS IS HOW YOU DIG: convert a solid type into a FOG and you
     have cut a real tunnel. Point "into" at a solid type instead and
     the module BUILDS walls.

     "EMPTY" IS NOT ON THE LIST AND YOU DO NOT NEED IT. It is cell id 0
     and a const on the class rather than an asset, so it cannot be
     named - a Fog does the same job.

     CAREFUL WITH HAZARD. Nothing in the game filters cell contact
     damage by faction, so terrain you create will hurt YOU as happily
     as anything else. That is exactly what the game's own Crawler
     Laser does - ten types into Hazard at radius 4 - and it is the
     only stock weapon that uses this feature at all.

     BEAM-ONLY WITHOUT WEAPON FORGE, and that is the game's limit
     rather than a choice: HitscanWeapon is the sole caller of
     Level.ConvertCells, even though the field sits on every weapon.
     Weapon Forge extends it to projectiles and lobbed shots. With that
     mod absent this still works on beams, which is what the base game
     does.

     A type you leave out of "convert" is a type your weapon cannot get
     through, which is a fair way to keep Obsidian meaningful.

  AmmoEffect { trigger, seconds, infinite, refill, includeHealth,
               resource }
     Aliases: "infiniteammo", "freeammo", "reload".
     (NOT "ammo" - that one already means "which resource this weapon
     spends", on WeaponResourceEffect.)

     FREE SHOTS, as a buff or as a passive.

       { "type": "infiniteammo", "trigger": "kill", "seconds": 3 }
       { "type": "infiniteammo", "trigger": "always" }
       { "type": "reload", "trigger": "kill", "infinite": false,
         "refill": true }

     trigger    "kill" = a window after every kill (the buff shape).
                "always" = passive, permanently on.
     seconds    how long the window lasts. A series, so a level can buy
                a longer buff. Ignored by "always".
     infinite   default TRUE - shots cost nothing while it is open.
     refill     top every AMMO tank up at the moment of the kill.
                Instantaneous, so it pairs with a short window or with
                none at all. "every kill reloads you" is a legitimate
                and far tamer module than permanent free fire.
     resource   optional - restrict to ONE resource, so a module can be
                "infinite White" rather than infinite everything.

     IT NEVER MAKES HEALTH INFINITE, AND THAT IS THE WHOLE DESIGN.
     The obvious field, Unit.Data.HasInfiniteResource, is read by
     Shooter.OwnerHasResource and looks perfect. But its setter does

         foreach (ResourceTank t in GetAllTanks()) t.isInfinite = value

     and ResourceTank.Value's setter is

         if (this.isInfinite && this._value > value) return

     - an infinite tank REFUSES TO GO DOWN. Health is a ResourceTank,
     and DamagableResource.Damage is literally "tank.Value -= amount",
     so that one flag makes the ship completely invulnerable. Shipping
     the obvious implementation would have shipped god mode wearing an
     infinite-ammo label.

     So the flag is never touched. This sets isInfinite per TANK and
     skips every pool a DamagableResource guards - the game's own
     definition of "something you can lose", asked of the components
     rather than hardcoded to Health. For real invulnerability use
     "invuln" or "laststand"; both have cooldowns.

     includeHealth  OFF BY DEFAULT AND WORTH LEAVING OFF. The game's
                own RefillResources() fills every not-SHARED tank, and
                MONEY IS THE ONLY SHARED RESOURCE IN THE GAME - so
                health is in that list and a naive refill is a FULL
                HEAL ON EVERY KILL. Turning this on gives you exactly
                that, deliberately. The build log warns you.

     Only tanks THIS module switched on are ever switched off, so two
     ammo modules cannot cancel each other and the debug menu's own
     infinite-resource toggle is never stomped.

  StealthEffect { trigger, seconds, idleSeconds, revealOnFire,
                  revealSeconds }
     ENEMIES LITERALLY CANNOT SEE YOU. This is the game's own mechanic,
     fully implemented and previously reachable only from the debug
     menu: Vision.IsVisible is exactly
         return !component.ComponentData.IsInvisible

     And it does more than stop new aggro. AIAgent CLEARS AND REBUILDS
     its visible-enemies list from Vision every update, so everything
     currently hunting you drops you on its next pass. That pass is
     0.25s on 66 of the 68 prefabs with a Vision, which is also why a
     duration under about 0.3s will not register at all.

       { "type": "stealth", "trigger": "dash", "seconds": 1.5 }

     trigger:
       "dash"    vanish for "seconds" on every dash - a blink
       "idle"    GO TO GROUND: hidden once you have not fired for
                 "idleSeconds". Needs no reveal rule of its own -
                 firing un-hides you by construction
       "sprint"  cloaked while you hold sprint. Self-limiting, since
                 sprinting already burns fuel
       "kill"    a window after each kill
       "hit"     a window after taking damage - reposition instead of
                 tanking
       "always"  permanent, subject to revealOnFire

     REVEALONFIRE DEFAULTS TRUE AND IT IS THE WHOLE BALANCE OF THIS.
     Vision checks nothing except the flag, so shooting from stealth is
     otherwise completely safe: a cloak without this is not a stealth
     mechanic, it is an off switch for the enemy AI. Setting it false
     is deliberate rope and the log says so.

     Several stealth modules can be installed at once; if ANY of them
     currently grants, you are hidden.

  LastStandEffect { onThreshold, threshold, onKill, seconds, cooldown }
     YOU CANNOT DIE FOR A MOMENT.

       { "type": "lastStand", "threshold": 0.25, "seconds": 3,
         "cooldown": 20 }

     Uses DamagableResource.IsInvincible, and the name misleads, so be
     precise: the game does
         if (IsInvincible && tank.Value <= 0f)   -> floor the tank at 1
     Damage still lands and the bar still drops. You simply cannot be
     finished. So this is a SAFETY NET, not a shield - which is a
     genuinely different card from "invuln" above even though the
     titles sound the same.

     onThreshold  arm when your LOWEST pool hits "threshold" (0.25 =
                  a quarter). Checked across every pool you can lose,
                  so a shield resource counts. On by default unless you
                  asked for onKill instead.
     onKill       also arm on a kill - turns a safety net into a reward
                  for pushing forward. Both can be on.
     cooldown     counted from when the window OPENS, so "3 seconds
                  every 15" means what it says rather than 3 + 15.
                  A cooldown of 0 is refused and reset to 15, because
                  without one this is not a last stand, it is
                  immortality.

WEAPON effects (use with "target": "weapon"):
  ModifyWeaponProperty { targetProperty, operation, deltaCalculationMode,
                         value }
     targetProperty: FireRate, BurstSize, BurstDelay, ProjectileCount,
       Spread, AngleVariance, AngleOffset, KnockbackForce, Cost, Range,
       Speed  (Damage is intentionally unavailable - see below)
     operation:
       "Add"       (default) the value is ADDED to the stat
       "Multiply"  the stat is MULTIPLIED by the value, so 1.5 = +50%
                   and 2 = double. This is the easy way to write a
                   percentage without knowing the weapon's base number.
                   CAREFUL: 0 wipes the stat out entirely, and anything
                   below 1 makes it worse (which is a perfectly good way
                   to build a deliberate downside).
     deltaCalculationMode: how "value" is read BEFORE the operation
       "Constant"     use it as-is  (e.g. +1 projectile)
       "FromOriginal" value * base stat  (0.25 = a quarter of base)
       "FromCurrent"  value * current stat
       Leave this on Constant unless you want the effect to scale with
       whatever other modules have already done.

  ExtraWeaponStatEffect { targetProperty, operation,
                          deltaCalculationMode, value }
     The stats the game's own list above CANNOT REACH. Its
     targetProperty is a fixed enum of twelve baked into the game's
     assembly, and WeaponBase has 33 settable properties - so anything
     outside those twelve needs this instead. Same operation and
     deltaCalculationMode meanings, deliberately, so there is only one
     model to learn.

     targetProperty:
       "PushForce"     how hard your shots SHOVE what they hit
       "WarmupTime"    the minigun spin-up before a held weapon fires
       "BarrelLength"  how far in front of the ship a shot is born

     BARREL LENGTH IS SMALL EVERYWHERE EXCEPT A SHOTGUN, where it is
     very real: every pellet spawns at the same point, so a longer
     barrel pushes the whole cone forward and clear of your own hull.

     Shortcut: "type": "pushforce", "warmuptime" or "barrel" picks the
     stat for you, so the common case is one line:

       { "type": "pushforce", "value": 60 }

     PUSH IS NOT KNOCKBACK, and the game has both:
       KnockbackForce  = the RECOIL on your own ship. It is one of the
                         twelve above, on ModifyWeaponProperty.
       PushForce       = the shove applied to WHAT YOU HIT. This one.
     People usually mean PushForce when they say knockback.

     TWO THINGS THAT WILL SURPRISE YOU ABOUT PUSH:

     1. A PIERCING SHOT NEVER PUSHES AT ALL. The game returns out of
        Projectile.OnObjectHit at the piercing branch, before the push
        is applied. So this effect and a PierceCap module CANCEL EACH
        OTHER OUT - the push simply stops happening, with nothing in the
        log. The build log warns about it when you use push.
     2. The shove fights the target's MASS and DAMPING, which vary
        enormously (the ship is 1 x 0.5, a common Cross 5 x 6, a Queen
        200 x 4). One number cannot feel the same on everything: a value
        that sends a Cross flying barely nudges a Queen.

     Stock weapons sit around 20-200 for push. For WarmupTime, NEGATIVE
     is the useful direction - a faster ramp - and note warmup is inert
     on gadget-fired weapons, which bypass the Shooter entirely.

  WeaponCosmeticEffect { shootSfx, continuousShootSfx, startSfx,
                         releaseSfx, warmupSfx, reloadSfx,
                         muzzleParticle, reloadParticle,
                         shake, shakePreset, rumble, rumblePreset }
     HOW THE WEAPON FEELS, without changing a single number. The ten
     properties on WeaponBase that no stock effect can reach: six sound
     ids, the muzzle flash and the reload puff, the camera kick and the
     controller rumble. Nothing here affects damage, rate or anything
     else a stat line would show - it is pure presentation.

     Aliases: "cosmetic", "feel", "shake", "rumble", "muzzle",
     "weaponsfx", "weaponcosmetic".

     WEAPON GRID ONLY. Like every effect that modifies a weapon, this
     one only runs for a module connected to a WEAPON's grid. On the
     ship grid it does nothing at all - and it cannot warn you at
     runtime, because the effect simply never runs. The build log says
     so when the module is built.

     THE SOUNDS
       "shootSfx"            every shot
       "continuousShootSfx"  the loop a HELD weapon makes (beams,
                             miniguns). Nothing starts the loop on a
                             weapon that fires discrete shots.
       "startSfx"            once, when you pull the trigger
       "releaseSfx"          once, when you let go
       "warmupSfx"           the spin-up whine, if the gun has a warmup
       "reloadSfx"           on reload

     A game sound is named the way the audio database names it, with
     slashes - "Weapons/Shotgun/Shoot". All 259 are listed in
     SOUNDS.txt next to this file, 44 of them under WEAPONS. A custom
     .wav from Weapon Forge's sounds folder works too when that mod is
     installed. "shootSfx" also answers to "sfx" or "sound".

     A NAME THE MOD CANNOT FIND IS REFUSED, NOT ASSIGNED, and that is
     deliberate: an unknown sound id plays nothing at all, so writing
     a typo through would leave the gun SILENT rather than merely
     unchanged - a cosmetic module doing damage. The weapon keeps its
     own sound and the log names the file and the key.

     Note about 70 of the 259 entries are declared with NO CLIP. They
     resolve perfectly and play nothing; SOUNDS.txt marks every one.

     THE MUZZLE FLASH
       "muzzleParticle": "MuzzleParticle Laser"
     Swaps the whole particle prefab, so shape and colour change
     together. The eleven the game ships are "MuzzleParticle" plus
     Beacon, CrawlerLaser, Cross, CrossAlpha, Drone, Fly, Laser,
     LaserRed, Popper, PopperRed and Sniper. "reloadParticle" is the
     same idea for the reload puff and is rarely worth setting.

     (Weapon Forge's muzzleColor / muzzleSprite keys RESHAPE a weapon's
     existing flash. Use those for fine control over a weapon you
     wrote; use this to swap one wholesale on any gun you pick up.)

     THE CAMERA KICK - TWO WAYS TO ASK, and the first is the one you
     want:

       "shake": 1.5        MULTIPLY the weapon's own kick
       "shakePreset": "Shake_Gunshot_Medium"   REPLACE it

     Scaling works on any gun without naming anything, and it keeps
     that gun's own character - the vibrato, the randomness, the angle
     - instead of flattening every weapon into the same thump. It
     scales STRENGTH ONLY, never duration: "harder" and "longer" are
     different asks, and a stretched shake is nausea rather than
     feedback. Capped at 5x.

     A WEAPON WITH NO KICK OF ITS OWN HAS NOTHING TO MULTIPLY, so
     "shake" does nothing there and the log says so. That is not an
     oversight - inventing a kick on a gun that never had one is a
     decision, especially for a BEAM, which fires continuously and so
     would shake every frame. Use "shakePreset" to make it deliberately.

     The twelve stock presets: Shake_Gunshot_Small, Shake_Gunshot_
     Medium, Shake_Collision, Shake_Excavate, Shake_Explosion_MIN,
     Shake_Explosion, Shake_Explosion_Long, Shake_Explosion_MAX,
     SmallExplosion, LargeExplosion, Shake_Shipdamage, Shake_Wound.

     Set both and the named preset wins - naming one is the deliberate
     act, the number is only an adjustment to the weapon's own.

     THE RUMBLE works exactly the same way ("rumble" scales,
     "rumblePreset" replaces), with one caveat worth reading:

     RUMBLE IS GAMEPAD ONLY. On keyboard and mouse it does nothing at
     all, and even on a pad it is scaled again by the rumble setting in
     the game's options. So this is a key that can do nothing for a
     player through no fault of yours. The module card prints
     "RUMBLE (PAD)" rather than leaving them to guess, and the build
     log says it once. Motor speeds are clamped to the hardware's 0-1
     range, so a big multiplier on an already-strong preset simply
     reaches maximum.

     The eight stock presets: "Rumble WeaponShot" plus Small, Medium,
     Large, Flame or Derbis, and "Rumble Ship" plus Boost, Damage or
     Death.

     "shake" and "rumble" are both SERIES, so a green-crate BoosterCore
     beside the module can make the kick grow with its level.

       { "type": "cosmetic",
         "shootSfx": "Weapons/Shotgun/Shoot",
         "muzzleParticle": "MuzzleParticle Sniper",
         "shake": 1.6 }

  WeaponResourceEffect { resource, free }
     Changes WHICH RESOURCE the weapon spends - a Caps gun that runs on
     Electron. A different kind of module from "+10% fire rate": it
     changes what your build is made of, and frees the weapon from
     competing with your others for the same tank.

       { "type": "ammo", "resource": "Resource Electron" }

     THE TRAP, and it fails silently. The game checks the tank before
     every single shot:
         OwnerHasResource = HasInfiniteResource || Cost == 0
                            || GetResource(ResourceUsed) >= Cost
     Point a weapon at a resource the ship has NO TANK OF and that check
     never passes, so THE WEAPON SIMPLY WILL NOT FIRE - no error, no
     log, looking exactly like the module broke the gun. Either pair
     this with a ModifyResourceCapacity effect for the same resource, or
     set

       "free": true

     which zeroes the weapon's cost so it never consults a tank at all.
     That is the safe option, but "free ammo" is a far bigger balance
     change than "different ammo", so it is off by default. The module
     card names the resource precisely because it is the only place a
     player can find out why their gun went quiet.

     WHY DAMAGE IS BLOCKED. It is a genuine bug in the game, not caution
     on our part. Eleven of the twelve stat appliers ASSIGN their result
     (weapon.FireRate = value), but Damage does
         weapon.Damage = new Damage(weapon.Damage.amount + value, ...)
     and "value" there is ALREADY current+delta - so the base damage gets
     counted twice. A "+2" would actually give you +2 plus another whole
     copy of the weapon's base damage. Use an explosion / discharge /
     burn effect to add damage instead.
  IncreaseExplosionRadiusEffect { increaseAmount }
  AddImpactExplosionEffect      { }        projectiles explode on hit
  AddBurnEffect        { amount, costPerProjectile, costResource }
  BurnTickRateEffect   { ticksPerSecond }
     Speeds up how fast BURN ticks on enemies. ticksPerSecond is added to
     the burn tick FREQUENCY while this module is equipped, and stacks
     additively across equipped copies. e.g. burn normally ticks ~1/sec;
     two +0.1 modules make it tick ~1.2/sec (so ~1.2x burn damage/sec).
     - Affects ENEMIES only: burn that enemies put on YOU still ticks at
       the normal rate.
     - This effect does NOT add burn on its own - pair it with a burn
       source (AddBurnEffect, or a burn weapon).
     - Hard-capped so stacking can't run away - see the cap note below.
  BurnColorEffect      { color } OR { rgb: true, rgbSpeed }
     Recolors the BURN FLAMES on enemies while equipped.
       color          a game color name (ColorBlue, ColorPurple...) or #hex.
       rgb            true = ignore color and cycle a rainbow over time.
       rgbSpeed       rainbow speed, hue cycles/sec (default 0.5). rgb only.
       includeTerrain true = ALSO recolor burning terrain/world fire, not
                      just enemies (default false).
     - Your OWN on-fire flames are NEVER recolored (only enemies, plus
       terrain if includeTerrain is on). Like the tick rate, it does NOT
       add burn - pair with a burn source. If several are equipped, the
       most recent one wins (its color AND its includeTerrain setting).
  AddExplosionEffect   { damageType, damageAmount, costPerProjectile,
     costResource, addImpactExplosion, addTimeoutExplosion,
     explosionRadiusIncrement, burn }
  AddDischargeEffect   { chainLengthIncrement, damageIncrement, impact,
     timeout, costPerProjectile, costResource }     the "spark" arc
  Phasing              { }
     While equipped, your PROJECTILES pass through terrain (walls) but
     still hit enemies. No params. (Projectile weapons; for a phasing
     laser use Weapon Forge's per-weapon phasing flag.)
  PierceCap            { pierceCap, falloff, explodeOnLimit }
     While equipped, turns PIERCING on for your projectiles and caps it:
     they pierce THROUGH pierceCap enemies, then vanish on the next
     contact (that enemy still takes the hit). Caps STACK if you equip
     several. Options:
       pierceCap       enemies pierced before it vanishes (default 2)
       falloff         damage lost per enemy pierced (0.2 = -20% each)
       explodeOnLimit  explode when it hits the cap
     (Projectile weapons only.)

  WHERE THE NUMBERS SHOW UP
  Hovering the MODULE (on your ship grid) shows what THAT module adds -
  "PIERCE +2" (and, while installed, the running ship total as old > new),
  or "PHASING ON". Hovering the WEAPON shows the COMBINED total for that
  weapon - "PIERCE 4" / "PHASING ON" - adding the weapon's own built-in
  pierce (Weapon Forge "pierceLimit") to every equipped pierce module.
  NOTE: the game only draws effect lines for a module that's on the SHIP
  GRID - a module sitting in the SHOP list shows just its name/description
  (that's stock behavior, all modules are like that).

The burn/explosion/discharge effects only fire on PROJECTILE weapons.
Keep weapon stats sane: ProjectileCount/BurstSize should end >=1,
FireRate stays >0, Spread >=0 (it clamps).

Resource names: Health, Stamina, Caps, Electron, Fuel, Gel, Tech.
(Money is currency - not usable as a module resource.)

BURN TICK-RATE CAP
------------------
Burn can never tick faster than a set number of times per second, no
matter how many BurnTickRateEffect modules you stack. The cap defaults
to 100 ticks/sec and lives in the BepInEx config file
(BepInEx\config\com.sugarheady.moduleforge.cfg) under [Burn] MaxTicksPerSecond -
edit it there and restart to change the ceiling. (The game can only tick
burn once per frame, so a cap above your frame rate just means "every
frame".)

 6. ICONS & COLOR
----------------------------------------------------------------

Icons are module sprites named "HUD_GridTiles_0" to "_44" or
"HUD_Modules_0" to "_35". THEY ARE NOT ZERO-PADDED: it is
"HUD_GridTiles_7", not "HUD_GridTiles_07". A padded name resolves to
nothing at all - the build log used to describe the convention as
"HUD_GridTiles_NN", which reads as two digits and is where the padding
comes from. Both mods now accept a padded name, use the right asset,
and tell you the real spelling.

ALL 81 OF THEM ARE LISTED IN "MODULE ICONS.txt" next to this file,
with which stock module uses each one - and "Module Icons.html" DRAWS
them all at size, filters by name or by module, and copies a name when
you click it. The number tells you nothing about the picture, so start
there rather than guessing.

Handy ones, for quick reference:
  Stat Up 12  Regen 17  Shield 34  Extra Projectile 10  Fire Rate 4
  Spread 5  Projectile Speed 15  Range 11  Burn 40  Explosion 39
  Spark 41  Power Core 18   Burst = "HUD_Modules_17"
The Module Builder page has a dropdown for these.

An icon cannot animate - it is assigned once and nothing ever ticks
it - so naming an animation gets its first frame. You can pick WHICH
frame though: "mysheet:3" takes frame 3. That works on the game's
numbered sprite runs as well as your own sheets. Frame numbers are
0-based, and on a stock run the number IS the one in the sprite name.

color: a game ColorAsset name (ColorWhite / ColorOrange / ColorPurple
/ ColorBlue / ColorRed / ColorYellow / Color Tech / ColorPower) OR a
hex value like "#ff5555" (a new color is made on the fly).

 7. AVAILABILITY
----------------------------------------------------------------

source:
  "loot"  only from crates/bosses (default)
  "shop"  only in the shop
  "both"  both
  "none"  NEVER offered - no drops, no shop. The module is still built and
          registered, so it is handy for parking a definition, or for
          testing something without it cluttering your runs.
shopPrice        cost in money (default 100)

PAYING WITH INGREDIENTS AS WELL AS MONEY  ("shopCost")
------------------------------------------------------
The shop's price is a LIST of currencies, not a number, and the game
already draws one icon per currency and reddens the ones you cannot
afford. So this needed no new UI - only the keys to fill the list.

  "shopPrice": 400,
  "shopCost": { "Chip": 1, "Fiber": 2 },

That costs 400 money AND 1 Chip AND 2 Fiber, and the shop shows all
three. Ingredients stack ON TOP of the money price - which is what
every one of the game's own 62 shop entries does. For an
ingredient-only cost, write "shopPrice": 0.

THE FIVE THE GAME ACTUALLY TRADES IN:
  Chip        Fiber       Gland       Powerstar       Generator

  Two of those are stored under a different name than the one on
  screen - Fiber is "Coral" and Generator is "Shell" - and BOTH
  spellings are accepted, because the name you saw in game is the one
  you are going to type.

  Four more exist and NOTHING IN THE GAME HANDS THEM OUT: Bond, Ex,
  Face and Strange Ball. They are accepted with a warning rather than
  refused (a game update could start dropping them), but a price in
  one of them can never be paid.

  You can also name any ship RESOURCE - "Tech", "Purple", "Fuel" -
  and it is taken off that tank.

WHOLE UNITS ONLY. The shop counts in integers, so 0.5 is zero and is
dropped with a warning. That is a crash guard as much as tidiness:
the game's purchase code subtracts a currency WITHOUT checking the
ship can hold it, while the can-I-afford check quietly answers "you
have 0" - and a cost of 0 is the one value that passes the check and
then dereferences nothing on the way out.

MAKING IT MORE EXPENSIVE EACH TIME  ("shopCostIncrement")
  "shopCost": { "Powerstar": 1 },
  "shopCostIncrement": { "Powerstar": 1 },

  Adds one more Powerstar to the price after every purchase, exactly
  the way "shopPriceIncrement" does for money. The game matches an
  increment to the price of the SAME currency, so you can escalate the
  money and leave the ingredient flat, or the other way round. An
  increment naming a currency that is not in "shopCost" is dropped -
  there would be nothing for it to raise.

HIDING IT UNTIL YOU HAVE FOUND ONE  ("shopUnlock")
  "shopUnlock": "Powerstar"          (or a list: ["Chip","Powerstar"])

  Keeps the item out of the shop entirely until you have picked up
  that ingredient at least once this run. It is the game's own gate -
  seven stock items use it.

  It is DELIBERATELY SEPARATE FROM THE PRICE. The stock items always
  pair the two (the Fiber item is hidden until you find Fiber), but
  they answer different questions, so you can gate on one thing and
  charge another. Leave it out and the item is on sale from its
  unlock level as usual, showing a red price you cannot pay yet.

  A GATED ITEM IS NOT TIED TO A STATION TIER. Once you have found the
  ingredient it appears in the next shop you open, whatever
  "shopUnlockLevel" says - that is how the game's own gated items work
  (they are added as a shop opens, never rolled from a station's list).
  The build log says so: "Added ... HIDDEN until you have found
  Powerstar". Until 2026-09-27 a gated item was ALSO put in the
  station's list, which ignores the gate, so it could be on sale at the
  very first station (R19 test 270). Fixed.

shopPriceIncrement  how much is ADDED to the price every time the module
                 is bought (default 0 = the price never changes).

                 HOW THE GAME DOES IT: PUNK escalates repeat purchases by
                 adding a FLAT amount each time - it is NOT a percentage
                 and it does not compound. A module priced 300 with an
                 increment of 500 costs 300, then 800, then 1300, 1800...
                 Real values from the game's own shop table:
                   Fire rate / Proj speed / Spread / Burst / Range
                                            300  then +500 each buy
                   Extra projectile         2500 then +1500 each buy
                   Add Health               200  then +500 each buy
                   Add Fuel / Add Stamina   200  then +400 each buy
                   Power core / Regen       1000 then +1000 each buy
                   Shields                  4000-5000 then +1000 each buy
                 Most one-off modules simply leave the increment at 0.

                 NOTE: the game only re-stocks and re-prices an item that
                 is flagged repeatInShop, so setting an increment turns
                 repeatInShop on for you (unless you set it yourself).
shopPricePercent friendlier way to say the same thing: the increment as a
                 share of the base price. 167 on a 300 module = +500 per
                 buy, matching the stock stat modules. Ignored if
                 shopPriceIncrement is set.
shopUnlockLevel  how many STATIONS you must unlock before it can appear
                 in the shop (default 1; 0 = the very first shop).
                 PUNK gates the shop by station count.
lootWeight       drop chance vs other modules in the same crate pool
                 (default 10; stock modules sit around 10).
repeatInShop     true = the shop may offer this module MORE THAN ONCE in
                 a run. Off by default: the game drops a module from the
                 pool once you have bought or picked one up. Setting
                 shopPriceIncrement turns this on for you, since a rising
                 price only makes sense on a repeat buy.

Custom modules are registered at startup, so save/continue works.
Note: each shop tier rolls once as you pass it - to see a new shop
module, start a fresh run.

----------------------------------------------------------------
 8. BUFF INDICATOR - WHERE THE SETTINGS ARE
----------------------------------------------------------------

THE INDICATOR IS OFF BY DEFAULT, globally, on purpose. The game's
status area sits right next to the ammo / fuel / health readouts, so
anything drawn there is an overlay on top of the things you actually
need to see. Switching it on is a CONFIG FILE edit, not a JSON one:

  BepInEx\config\com.sugarheady.moduleforge.cfg
  section [Buff indicator]

  Style            "off" (DEFAULT) - nothing is drawn
                   "feed"  - the game's own status line, the one that
                             says "Fuel low"
                   "icons" - a row of icons beside the minion counter
                   "both"
  Label            "effect", "seconds", "stacks", or "icon"
  MaxFeedLines     the most status lines this mod may occupy at once
                   (default 3). A hard backstop, so the feed can never
                   grow over the HUD however many buffs are running.
  IconSize         side of one icon in pixels (default 28). The widget
                   is BORROWED from the minion counter and arrives at
                   whatever size that prefab was authored with, so this
                   is the number that decides how big it looks.
  ShowTimedStates  also report ongoing states
  ShowDebuffs      also report things working against you

WEAPON FORGE HAS ITS OWN IDENTICAL BLOCK in
com.sugarheady.weaponforge.cfg. The two are deliberately independent so
either mod works with the other absent - which does mean that if you
set only one, module buffs and weapon buffs will look different. The
mods log a warning once at startup if the two disagree.

An effect's own "buffIndicator" key picks the ICON. It does nothing at
all while Style is "off".
